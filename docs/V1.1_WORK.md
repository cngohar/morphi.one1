## 1. Procedural themes — local review slice

- Recipe-generated, gamut-mapped OKLCH colors; six named harmonies plus free
  sampling, continuous hue, contrast targets 3.3/5.5/9, chroma ≤0.19.
- Contrast checked after 8-bit hex conversion, and CIE76 separation under normal
  vision and Machado severity 1.0, applied in linear sRGB. Safety margins are
  3.1 symbol/edge, 4.7 text, 1.55 back, 22 color difference and ≤1.25 decoration.
- At most eight palette attempts, then a documented, verified preset. The four
  anchors are the PLAN's Shapes/Ocean/Garden/Candy, rather than unsafe legacy
  v1 app palettes. `check-palettes.ts` reads the PLAN's table and rejects drift.
- Immutable `theme-2026-10-26-1` JSON configuration; generator
  `oklch-machado-1`; five style records, four containers, ten generated
  silhouettes from eight families, five own-item scatter arrangements.
- Memory uses generated symbols, borders, fills, proportions and gaps; Block
  uses generated piece colors, cell surfaces/shapes and gaps. Board topology,
  piece definitions, pair count and gameplay are unchanged. The shared symbol
  set is generated in Block snapshots but not painted onto Block pieces.
- Solo theme history and snapshots use IndexedDB, with bounded in-memory
  fallback. Ranked starts receive a server-resolved snapshot; local D1 stores
  versions and snapshots at start and completion. Pending results carry the
  snapshot separately from the scored wire payload. Legacy queued v1 runs
  remain valid and are explicitly labeled `curated-v1`.
- Freshness draws at most eight candidate seeds against the preceding three
  themes. It keeps the last accessible theme if all miss novelty. The current
  small family vocabulary shares symbol families in every round after the

## Owner screenshot follow-up — viewport sizing

During this slice the owner supplied a 1920×923 screenshot and explicitly
requested the already-planned sizing fix, then directed work to continue. The
image showed a roughly 642×472 panel and a 440px-wide card grid. The v1 CSS
capped the wrap at 690px and Memory/Block boards at 440/330px.

`src/lib/ui/game-shell.css` replaces those caps with available viewport and
container dimensions. In-play names now sit in the header (a separate line on
narrow portrait screens); the help/high-score panel spans the viewport and is
flush with the bottom. Clear gaps separate the game panel from both bands.
The scatter is behind the game, limited to its own items and outside the header
and bottom bands. The footer distinguishes a genuinely new family from a
completed zero-score family. Current game entrances remain; The Card is a
subsequent design/integration item, not implied accepted by this size fix.

Owner follow-up on 2026-10-27 identified that puzzle-item backgrounds were not
apparent. Code review confirms this requirement is only partially implemented:
the generator can select `none` (no items), and the renderer otherwise uses
fixed card/two block motifs at seeded edge positions, with a pre-blended color
and 20% opacity. Work 2 must complete and visually verify the required own-item
scatter on every generated puzzle; contact-sheet approval does not accept this
background behavior. See scope §2, “Background rule”.

`themes.spec.ts` now asserts ≥70% panel height on desktop, at least 95% use of
the board's limiting container dimension, full-width bottom anchoring and gaps,
and no scroll. It includes 1920×923 alongside the four required viewports and
runs the theme/surface checks in Chromium, Firefox and WebKit. Captures and
dimensions live under `build/v1.1-themes/`.
