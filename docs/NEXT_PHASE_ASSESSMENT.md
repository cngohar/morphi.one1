## Access and user actions

`/admin/sign-in` uses Google plus TOTP or a single-use recovery code; enrollment and reset are local OS-owner/TOTP commands (`src/routes/admin/sign-in/+page.server.ts:19`, `scripts/admin-local.ts:70`). Five invalid or replayed second factors cause a 15-minute lock; the fifth is rejected as an invalid code, subsequent attempts during the lock are rejected as locked. A local authenticated admin can reset web access; recovery codes are also blocked during the lock (`src/lib/server/operator.ts:85`, `:160`, `:271`). Operator sessions expire after 30 minutes or 10 minutes idle. Every web mutation except logout requires both Google and operator authentication less than 15 minutes old; this is a freshness check, not a new TOTP prompt for every individual mutation (`src/lib/server/operator.ts:174`, `src/routes/admin/[view]/+page.server.ts:222`).

The code defines admin, moderator and support permissions, checked server-side per action (`src/lib/operator-permissions.ts:1`, `src/lib/server/operator-http.ts:5`). Admin has all currently implemented permissions; moderator can moderate, rename and manage cases; support has moderation lookup. CLI moderation checks roles too (`src/lib/server/moderation.ts:13`). The local bootstrap assigns admin and web enrollment assigns admin; enrollment currently refuses a second web operator (`scripts/admin-local.ts:40`, `src/lib/server/operator.ts:216`). No web role editor or public role-assignment endpoint was found. D1 protects deletion of enrolled admin accounts and removal/demotion of the last enrolled web admin (`migrations/0003_v1_operator.sql:35`); this is not a full multi-admin management system. No impersonation or production test/fixture login was found in the inspected routes and action allowlists; test fixtures exist in tests only.

## User and game statistics

The user's own profile shows public name, per-family completed and ranked counts, last played, current scoring-version bests, and up to 30 recent saved results including date, family/group and score (`src/lib/server/runs.ts:301`, `src/lib/components/account/ProfileContent.svelte:88`). These are saved account rounds, not all guest play. It does not display join date, average score, activity timeline or ban history.

Admin lookup shows public name, recent saved round ID/family/score, hidden flag and current ban flag, up to 25 matches (`src/routes/admin/[view]/+page.server.ts:102`). Hidden status and ban status are admin-only there; lookup is not a full profile. A verified privacy export separately exposes Google name, email, join date and raw saved rounds, 100 at a time (`:328`); this sensitive request workflow is not a general stats view. No admin user view provides last activity, full total/per-game plays, completion rate, best/average by game, ranked/solo breakdown, activity timeline, warning history or comprehensive ban/hidden history. Audit may contain individual moderation events, but is not a user timeline. Google profile fields and email require an explicit privacy decision before broader display.

Dashboard computes live counts of accounts, retained saved completions, retained ranked starts/claims, eligible-entry approximation, hidden scores, bans and distinct deletion targets; completed rounds by day for seven days; all retained saved completions grouped by family; and seven-day anonymous event totals (`src/routes/admin/[view]/+page.server.ts:78`). For each of Block, Memory and Connect, the available per-game dashboard stat is saved completed-round count. There is no per-game UI for plays, abandonment, score average/best, duration average, ending breakdown, ranked/solo or band breakdown. Raw completed records contain score, seconds, family, ranked, rules group and moves; privacy export is user-scoped, not a game report (`migrations/0001_panoramic_turbo.sql:17`). Anonymous events contain family for a limited opt-in event set but the dashboard groups by event, not family (`src/lib/server/measurement.ts:1`). No complete guest or abandonment dataset exists. Pruning removes expired starts and anonymous events older than seven days (`src/lib/server/retention.ts:20`); counts therefore are not lifetime starts. Dashboard entry count omits the current-score-version filter used by actual leaderboards (`src/routes/admin/[view]/+page.server.ts:80`, `src/lib/server/runs.ts:375`). Do not combine these populations into a completion rate without a defined measurement policy.

## Game controls and scoring

The existing scoring screen edits coefficients for all three families; there is no game management screen or individual game disable/delete operation. The global ranked switch only affects ranked play, not a particular game. Removing a game, hiding it from the selector, and deleting its history have no implemented admin meaning; selector inclusion currently lives in code (`src/lib/screens/PlaySession.svelte:251`, `src/lib/selector.ts:25`). No claim can be made about in-progress behavior for an unimplemented game change.

Scoring is already versioned: exact-key integer validation, 0–10,000 ranges, immutable database rows, current pointer and an atomic before/after audit; stale/concurrent saves conflict (`src/lib/engine/scoring.ts:7`, `src/lib/server/scoring.ts:29`, `migrations/0008_right_solo.sql:1`). Ranked start captures the live version; replay and saved result retain it, and current leaderboards compare only that version (`src/lib/server/runs.ts:140`, `:188`, `:281`, `:375`). Existing results and in-flight ranked rounds are not re-scored by a save. Solo rounds retain their selected version, including offline defaults. Floors are in game scoring logic; par-time editing is not in the editor. Reset defaults makes another version. Integration coverage exists in `tests/integration/runs.test.ts:400`; no tests were rerun in this assessment.

## Audit and undo

Only admin has `audit` permission. The viewer is newest-first, read-only, paginated by 25; no actor/action/target/date search or audit export is implemented (`src/lib/operator-permissions.ts:1`, `src/routes/admin/[view]/+page.server.ts:123`). Schema records actor, action, target, reason, before, after and time. Scoring records whole old/new values and versions, allowing fields to be compared, rather than separate per-field audit rows (`src/lib/server/scoring.ts:57`). Web page reads and CLI hidden-score listing are audited (`src/lib/server/operator.ts:202`, `scripts/admin-local.ts:134`). Privacy deletion records a minimal reference, not deleted personal data. There is no configured audit TTL; local pruning explicitly preserves audit. No limit-reached policy is implemented (`src/lib/server/retention.ts:20`). There is no app action to edit/delete audit, but no D1 trigger prevents a database operator doing so. Moderation reads before-state outside its mutation batch and case resolution hard-codes its before-state, so concurrent changes or repeated resolution can make audit before-values inaccurate (`src/lib/server/moderation.ts:34`, `src/routes/admin/[view]/+page.server.ts:311`). This needs hardening before relying on audit for automatic undo.

## Game ending and preserved flow

Game-specific end hooks persist first and call `onfinish` after their presentation (`src/lib/screens/PlaySession.svelte:501`, `:693`). Block ends on no fit **or placement cap**, with 450 ms end hold (`src/lib/puzzles/block-placement/logic.ts:247`, `Game.svelte:366`); Memory ends when all pairs match with a 1,150 ms win sequence (`src/lib/puzzles/memory/logic.ts:93`, `Game.svelte:360`); Connect ends when all pairs connect, even with empty cells, with fill as a bonus and a 1,000 ms normal hold (`src/lib/puzzles/connect/logic.ts:202`, `Game.svelte:181`). A universal “No moves left!” needs a separate cap wording if that cap can occur. No shared ending headline/kind/subline contract exists.

`recordResult` folds the Card into the stack then reveals the central result (`src/lib/screens/PlaySession.svelte:447`). Motion wrapper supplies 420 ms entrance, score-only 500 ms scramble and 350 ms exit from the current frame (`src/lib/ui/motion.ts:112`, `:145`, `:197`). Reduced motion skips shared fold/exit waits and settles shared result immediately (`src/lib/screens/PlaySession.svelte:99`). Memory/Block ending timers still wait under reduced motion and use ordinary timers; Connect uses a pausable delay and zero reduced-motion hold. Memory/Block timer callbacks lack the guarded handling used by Connect. This is an existing inconsistency to address in a later approved slice, not a change made here.

A future shared presentation needs per-game ending kind (run-over or completion), localized headline and optional data-driven subline, a motion slot and an owner-selected continue rule. Keep immediate durable completion, server replay, selected next family, preparation failure fallback, and game-specific entrance/finish behavior; presentation must never decide game completion or readiness. Follow message catalog, token-only colors, no object glows/shadows/bevels, motion wrapper and immediate reduced-motion settlement (`docs/puzzles/_TEMPLATE.md:58`, `src/lib/ui/motion.ts`). Existing preparation/result lifecycle coverage includes `tests/e2e/preparation.spec.ts`, `tests/e2e/app-card.spec.ts` and `tests/e2e/connect.spec.ts`; these were inspected as evidence, not rerun.

## Do not duplicate / proposed order

Reuse the existing operator panel and server permissions, Google/TOTP sessions and local enrollment, moderation and case workflow, privacy-request tools, append-style audit viewer, scoring editor and immutable versioning, account history, registry, shared Card/result flow, motion wrapper and preparation pipeline. Do not build a second panel or scoring system.

Proposed owner approval order: (1) user controls and agreed user statistics **with audit integrity and agreed undo alongside each action**; (2) centralized game controls and agreed game stats, preserving score versions and defining what data is measurable; (3) shared ending presentation. Ending is technically independent enough for a parallel local slice after its wording, behavior and contract are approved, but shared `PlaySession` changes and verification must be coordinated. This order is a proposal only.

## Questions for the owner

1. **Ban:** Current bans have no expiry and last until unban. Keep permanent, add temporary, or both? Which durations?
2. **Delete:** Current verified privacy and self-service deletes hard-cascade saved account data and remove leaderboard entries; no ordinary admin delete exists. For ordinary admin delete choose hide, anonymize or cascade for user data and boards; should it begin as reversible soft-delete?
3. **Scoring rollback:** Current manual edits/default reset create new versions. Confirm rollback must create a new version with old values, preserving all prior rounds and versions.
4. **Admin-only stats:** Currently hidden/ban flags and verified privacy export data are visible in limited workflows. Which exact additional statistics must admins see but players not see? Should private Google data remain confined to verified privacy export?
5. **Audit:** Currently admin-only, no TTL, no UI export, and no DB immutability guarantee. Who may view it, how long should it be kept, and should export ever be allowed?
6. **Undo:** Currently inverse moderation actions exist but no audit-driven undo, and privacy deletion is final. Which table actions must be undoable, and which explicitly final?
7. **Ending copy:** Confirm Block “No moves left!”, Memory “All pairs found!”, Connect “All pairs connected!”, and desired sublines: Block score/pieces, Memory pairs/time, Connect fill %. What wording should apply to Block's placement-cap ending?
8. **Ending behavior:** There is no interstitial today. Auto-advance after how long, tap to continue, or both? Under reduced motion should it appear immediately and for how long? Define early Next behavior while preserving the current result exit.
9. **Game delete:** No such control exists. Should it remove a game from the selector only, or also remove its history and stats? What happens to active rounds?
10. **Future game contract:** Currently manifests have no ending declaration. Confirm required headline, optional/required subline, ending kind and animation/continue behavior, including run-over versus completion.
