## Approved behavior

### Member flow

Add a Support entry to the existing account area. Provide a paginated ticket list, create form (subject, category, priority, message), and conversation view with chronological messages and Close. Show staff replies in the conversation and an unread-reply indicator in the support area. Mark read only when the member opens the conversation. No email notifications in this version.

Two states: Open and Closed. Closed tickets stay readable and reject further replies. No reopening, attachments, rich text, staff-only notes, assignment, department routing or automatic ban reversal. Staff may reply and close together atomically. If another actor closes the ticket before a reply commits, preserve the draft and explain the conflict.

### Categories and priorities

Approved protected defaults: General category and Normal priority. Other entries have stable ids; renaming preserves ticket relationships. Admin deletion transactionally reassigns all affected tickets, including closed tickets, to the corresponding default and records a content-free audit. Reject stale/deleted choices on submission with a recoverable form error. No cascading deletion of tickets when deleting taxonomy entries.

Banned members use the same categories and limits, without revealing ban evidence or internal moderation notes. Support access does not grant any other account permission. A ban does not delete a conversation or prevent reading staff replies.

### Approved initial limits

- Counting rule: trimmed UTF-16 code units (`String.length`), matching browser `maxlength`; a surrogate pair counts as two. Reject NUL characters.
- Subject: 1–120 characters after trimming.
- Message: 1–4,000 characters after trimming; enforce the same documented counting rule on client and server.
- Category/priority names: 1–60 characters; unique normalized names.
- Member ticket creation: 3 per hour, maximum 5 open tickets.
- Member replies: 10 per 10 minutes across their tickets.
- Staff replies: 30 per minute per operator, with existing operator protections retained.
- Enforce limits atomically on the server; do not count rejected writes as successful tickets. Return a useful retry time and retain the draft. Ban status does not relax these limits.

Render subjects, taxonomy names and messages as escaped plain text; preserve line breaks without HTML, Markdown or automatic link conversion. Bound request bodies before accepting message content. Never log message bodies or put them in audit records, analytics, URLs or browser persistence. Keep failed drafts in the current page memory only.

## Permissions and data safety

| Action                                                  | Member | Banned member | Moderator | Admin     |
| ------------------------------------------------------- | ------ | ------------- | --------- | --------- |
| Create/read/reply/close own ticket                      | Yes    | Yes           | As member | As member |
| Read/reply/change category or priority/close any ticket | No     | No            | Yes       | Yes       |
| Manage categories and priorities                        | No     | No            | No        | Yes       |

Every read and write checks authentication, ticket ownership or explicit staff permission on the server. Deny guest access and cross-member ticket access. Existing `support` operator role gains no staff access. Reuse operator second-factor/freshness requirements and same-origin mutation protections. Audit staff access/actions using existing conventions, without duplicating conversation content. Private responses must not enter shared caches or search indexes.

Use minimal D1 ticket/message/read-state and taxonomy storage plus bounded limiter state, integrated with the existing schema/migration conventions. Ticket creation plus first message, reply plus unread change, close, taxonomy reassignment/deletion and associated write audits must commit atomically. Use idempotency for retries/double submits. Paginate lists and conversations; use stable ordering and indexes. Keep this isolated from puzzle engines and scoring.

## Approved retention

Owner-approved policy: keep tickets/messages while the account exists, matching account-owned saved history; both self-service and operator privacy deletion remove owned tickets and every message in them through tested cascades. Closing a ticket does not erase it. Minimal staff audits remain under existing audit policy, without message/subject content. Pending-deletion accounts must not create or mutate tickets; existing lifecycle purge timing remains unchanged.

No closed-ticket expiry or scheduled deletion is introduced. Update the local privacy policy, retention inventory and request/deletion instructions for this policy. No public policy publication is authorized.
