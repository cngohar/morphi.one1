Memory roadmap: up to 100 total variants

Memory only, delivered in independently stoppable checkpoints. Recommendation: bounded Games admin work, an approved Memory matrix, then a pilot aiming for 10 total variants and reviewed expansion batches. The cap is 100 total Memory variants, including the existing four; it is not a quota. Block, Connect and Mahjong expansion remains future work.

Standing rule for every update and future family: a variant must make a meaningful gameplay rule or rule-setting change. Each matrix/brief must name its baseline and concrete rule difference. Colors, palettes, artwork, themes, animation, purely visual layouts and different seeds/deals do not create variants or increase the count. Board size/layout qualifies only when it changes gameplay rules or rule settings. Existing accepted identities and replay behavior are preserved.

The 100-total cap applies to Memory in this plan, not automatically to every family. Future family counts belong to their own plans; the rule-distinct definition applies to all families.

The No Man’s Sky comparison

Hello Games describes a procedural universe and continues adding generation capabilities and gameplay. The useful lesson is to improve what generators can express while generating instances on demand. Design judgment: players must notice fresh decisions, not just a large possible count.

Finite seeds and equivalent outputs mean “effectively endless” is a player-experience goal. Neither a large seed space nor the current selector proves an exact board will never repeat.

A master switch changes one family policy. New-round issuance checks that policy alongside a specific variant disable; an override cannot bypass a disabled dimension. Do not rewrite thousands of variant rows or alter immutable gameplay definitions. Existing rounds retain the previously agreed completion behavior.

Persist and identify the exact gameplay configuration used by each round. Keep current eligibility separate from immutable replay rules. For large directories, use indexed filters, stable unique ordering and cursor pagination. OFFSET is acceptable for small lists but costs more at deep offsets.

Source definitions, D1 operations and selective caching

LayerResponsibilityRecommendation
Family source / manifestEngine capability, validation, defaults and tested preset definitions.Keep executable logic here. Extract repeated preset data into family-local files when useful.
D1 — already presentLifecycle state, live configuration pointers, immutable score versions, sessions, history and audit.Extend existing patterns. Add immutable preset records only if runtime editing is actually required.
KV — already presentVersion-keyed immutable snapshots and the existing eventually fresh admin overview.Keep optional with D1 fallback. Stale KV must not decide authoritative eligibility or scoring.
Generated roundsSeed + exact preset/rules version + engine version reconstruct the round.Generate on demand. Store actual sessions/results as needed; do not materialize all possible boards.

A manifest does not become slow merely because it is a file. No benchmark establishes a manifest bottleneck. Identified growth risks are eager browser metadata, unbounded lists and per-variant database queries. Database definitions also require loading, validation and caching.

A few hundred compact source presets may be sufficient. At tens of thousands, avoid shipping the entire catalogue to every player. Retain the small family index, load relevant metadata on demand and bound admin responses. Game views and pools already load lazily.

KV updates can take 60 seconds or more to appear elsewhere. Use D1 for live decisions and immutable versions for replay. Editing a preset in place must never silently change an old checkpoint, ranked session or saved run.

D1 performance depends on query shape and rows read. Inspect query plans and row-read counts before adding indexes or storage. Source extraction improves maintenance; fewer fetched records and less loaded data improve runtime performance.

For two-tier administration, D1 is the searchable record store. R2 holds objects such as assets or exports; it is not a drop-in SQL table and is not required for preset management. Source still owns executable rules, schemas and defaults; “never in TypeScript” is too absolute. Add runtime-editable immutable preset rows only when the operator workflow needs them.

A global disable affects new authoritative starts only after the current policy is checked there, with concurrent-start behavior explicitly defined. A client may briefly display an old candidate. Eventually consistent KV cannot promise immediate global enforcement.
