## 2. The board — what a player sees

- **Board key:** `(family, UTC date)`. Example row label is only `Today's Memory` — family + date, never a variant, size, or puzzle number that identifies the variant.
- **Daily puzzle:** one per family per day, identical for every player that day (shared daily seed + one server-assigned variant, §3). A player may play the daily puzzle once ranked per family per day; replays that day are practice, unranked, and never enter the board.
- **Daily families (LOCKED 2026-11-09, owner):** every enabled family, every day, from day 1. No rotation. At v1.4 launch that is block, memory, and connect; each new family joins the daily set the day it is enabled.
- **Board page:** `/leaderboard?family=memory&date=YYYY-MM-DD`, default `date=today`. The family selector lists all enabled families (all are daily from day 1 — §2 above) plus families the viewer has already played. It never lists variants. Home stays one Play button — no family list, no variant list.
- **Monthly archive (LOCKED 2026-11-09, owner): PUBLIC.** It lives on the leaderboard page itself, via a date picker: `/leaderboard?family=<family>&date=YYYY-MM-DD`. Any guest can pick any past date and see that day's frozen board; a month list on the same page groups past days by month. No separate route, no sign-in, no admin-only gate.
- **Board content:** global public Top 25 by default (names + scores), with a "Show Top 100" toggle that expands the same board to 100 on the player's request (reads from `daily_best`, `LIMIT 100`, same indexed query — §4). The viewer's own rank and score show even if outside Top 25/100, and a percentile (**LOCKED 2026-11-09, owner: Top 1% / 5% / 10% / 25% / 50%**, computed at snapshot time — Top 1% = beat 99% of that day's players for that family, and so on). No raw variant, seed, or move data in the response.
- **Visibility:** global public, exactly like today. `src/routes/leaderboard/+page.server.ts` today has no sign-in requirement — any guest can view Top 25, sign-in only highlights their own rank. v1.4 keeps that. Friends-first is a later update, not v1.4.
- **Update cadence (owner already agreed in chat, 2026-11-08):** a new best updates the board, readers see a cached Top 25 refreshed every 1–5 minutes — NOT on a multi-hour timer. Cron does rollover at 00:00 UTC (start today empty) plus a monthly archive. Yesterday's board is NOT finally frozen at 00:00: it accepts late completions from rounds started yesterday until 02:00 UTC, then freezes finally (midnight-rollover rule, §10). A 6-hour refresh would kill the "come back to defend your rank" loop.
- **Streak:** one site-wide streak, +1 per UTC day on which the player completes at least one daily family. Shown as a count only (`Streak 7`), never with a variant or family breakdown. **Streak freeze (LOCKED 2026-11-09, owner): pro/premium players only, delivered as a STUB in v1.4 — not as working logic.** A freeze saves a streak when a pro player misses one day. ## 3. Daily puzzle — server-only variant, never sent to the client

- **Derivation (PLAN §403):** daily seed = HMAC-SHA256 over `UTC date | family`, keyed by a Worker secret `DAILY_SEED_SECRET` set via `wrangler secret` — never committed, never in the repo, never computable by a client. Reset at 00:00 UTC. Do NOT reveal the daily seed or puzzle before the player starts.
- **Variant pick:** the same HMAC output deterministically picks one enabled variant for that family that day (weighted pick over `variant_lifecycle` state `enabled`, reusing the existing enable/disable table from migration `0013`). The variant id is stored server-side only, in the new `daily_puzzle` table (§8). It is NEVER returned to the client, in any route, JSON, URL, or error. **In plain words: the daily puzzle IS the puzzle every player gets that day — one variant + one seed per family per day, identical for all players.** Generation: **LOCKED 2026-11-09, owner — Cron at 00:00 UTC pre-generates tomorrow's daily puzzle** (see §8; the daily puzzle exists before anyone plays).
- **Issuance — reuse `startRanked` (`src/lib/server/ranked-session.ts`):** add a daily issuance path that reuses its guards (player exists, not banned, account active, `game_lifecycle` family enabled, variant enabled, score-live version, caps: 30 sessions/hour, 10 abandoned). Differences, and only these: seed + variant come from `daily_puzzle`, not from `drawFreshTheme`/`randomSeed`; one ranked daily session per user per family per date (idempotent re-issue returns the same session, never a new seed); expiry 2h as today (`now + 7200000`). Do NOT change the practice/ranked issuance path.
- **Client contract for a daily round:** the client receives family, seed, engine version, score config version, theme snapshot, and the help/rules for _this_ round only — without a variant id or name. Teaching the rules of the round in front of the player is required to play it; naming the variant or listing variants is banned. The teaching is the round-rule line (§5A), not a variant title. **The daily round is server-issued (§8A.1):** the server resolves the variant from the `daily_puzzle` row and issues the round; the client never chooses, holds, or sends a variant id for a daily round. Practice rounds keep the existing client-side path unchanged.
- **Anti-farming:** the player cannot choose, skip, or re-roll the daily variant. If the daily session is abandoned, that day's ranked attempt for that family is spent (exact session id, same rule as ranked abandonment today). Practice rounds use the existing per-player random seed path and are never ranked.

## 4. Board storage and reads — never rank on read

- **New tables (migration `0015`, §8):**
  - `daily_puzzle(family, date, variant, seed, engine_version, score_config_version, created_at)` — PK `(family, date)`. `variant`/`seed` are server-only columns; no API may select them into a client response.
  - `daily_best(family, date, user_id, score, seconds, moves, created_at, updated_at)` — PK `(family, date, user_id)`. One row per player per family per day, best score only. Index `(family, date, score DESC)`.
  - `daily_board_snapshot(family, date, top_json, total_players, updated_at)` — PK `(family, date)`. `top_json` is the rendered Top 25 + percentile cut-offs, nothing else.
  - `streak(user_id, current, longest, last_date)` — PK `user_id`. One row per player.
- **Board read (`leaderboard()` in `src/lib/server/runs.ts`, rewrite):** read `daily_board_snapshot` from KV (`CONFIG_CACHE`, key `daily-board:{family}:{date}`, TTL 300s, same `cachedConfigRow` pattern as `src/lib/server/config-cache.ts`) or the Cache API; on a miss, compute Top 25 from `daily_best` with an indexed `ORDER BY score DESC LIMIT 25` query — never a window function over `completed_run`. Own rank = one indexed `COUNT(*) FROM daily_best WHERE family=? AND date=? AND score > ?` plus the viewer's own `daily_best` row. Delete `BOARD_GROUPS` and the `row_number() OVER (PARTITION BY user_id …)` query. That query is the current bottleneck: it ranks every ranked run in a group on every page view, with no `LIMIT` in SQL.
- **Board write:** in `saveRun`, a daily completion upserts `daily_best` only if the new score is higher (one atomic conditional statement, same pattern as the `play_session` issuance `INSERT … SELECT … WHERE` in `ranked-session.ts`). Then invalidate the snapshot key for that `(family, date)`; the next read recomputes it from `daily_best` (cheap, indexed, Top 25 only). A Cron Trigger every 5 minutes refreshes today's snapshots and rolls over at 00:00 UTC; a monthly Cron archives frozen boards. **No Durable Object and no Queue in v1.4** — PLAN §1007 and §986 order is cache first, then batch, then DO hot counters, then shard, and only on measured need. If the load test in §9 shows D1 write pressure, report it as the trigger for a v1.4.x DO/Queue follow-up; do not build them speculatively here.
- **Retention (pre-launch, no production users):** v1.4 does NOT migrate old per-variant leaderboard history. Migration `0015` starts the new boards empty. `completed_run` rows keep their internal `rules_group` as a replay/scoring key only — it is never a board key and never returned to a player. `pruneExpiredRecords` (`src/lib/server/retention.ts`) today never deletes `completed_run`; v1.4 adds a retention rule for it (**LOCKED 2026-11-09: 90 days, `move_log` archived to R2 by run id first, then deleted from D1** — replay already validated the run at submit). R2 binding: `RUN_ARCHIVE` (§8A.5), used only for this archive-before-delete.

## 5A. Round-rule line — teach the round, never name the variant (applies to EVERY family and EVERY variant)

Memory no-preview is an example only. The rule is universal, because a variant by definition changes gameplay (C2, `docs/puzzles/_TEMPLATE.md` 2026-11-06): if the gameplay changed, the player must be told what changed _for this round_, or the round is unfair/confusing. The variant _name_ is deleted; the variant's _rule_ is kept, in plain words, for that round only.

- **Definition:** one plain-language sentence (max one line) describing what is different in this round versus the family baseline. It is the help text that differs from the baseline variant's help — no new field, no manifest logic change. Derivation: `roundRuleLine(family, variant)` in `src/lib/ui/puzzle-presentation.ts` returns, in order: (1) the first help step present in this variant's `help.steps` but absent from the baseline variant's `help.steps`; (2) if no step differs, the variant's differing `help.note` (e.g. Connect `connect:rush-60` → `connect.rush.scoringNote` = "Connect all pairs before the 60-second clock runs out."); (3) if neither differs, the variant's differing scoring-row value rendered as a sentence (e.g. Connect `connect:board-8` → `connect.board8.size` = "8 × 8 grid, 8 pairs" → "This board is 8 × 8 with 8 pairs."); (4) if nothing differs, there is no extra line (baseline help only) — and a variant that reaches (4) must be fixed under §8E.2 instead of shipping without a line. Checked examples in code (HEAD `9e10b73`): Memory `memory:no-preview` → step `memory.noPreview.step3` = "Cards start face down. There is no free opening allowance." (`src/lib/puzzles/memory/messages.ts:544`); Memory `memory:trios` → "Turn over three cards per attempt."; Block `block:rows-only` → its differing step2; Block `block:rush-60` → its differing step3 (60-second clock); Connect `connect:full-grid` → its differing step3. **Correction to the rev 2–5 claim:** Connect `connect:board-8` and `connect:rush-60` do NOT have differing steps — their steps are identical to baseline; their differences live in a scoring row (board-8) and a note (rush-60). That is why §5A's step-only derivation returned no line for them and the teaching assertion failed. The widened derivation above fixes it without a manifest edit.
- **Where it is shown:** (1) on entrance, before the first move, as a one-line rule card under the family name; (2) in the Help dialog, under the family-only heading (`PuzzleHelp.svelte`, heading becomes `familyName(family)` only, steps stay per-round); (3) on the result screen, as a plain description, e.g. `Memory — cards started face down`, never as a variant title. It is shown for practice rounds and daily rounds alike.
- **Where it is NOT shown:** no variant id, no variant name, no variant list, no catalogue, no leaderboard group, no URL. The line must not contain the words of the variant's name as a label — it describes the rule, it does not title the variant.
- **Which rounds need it most:** any rule difference that is _not_ visible in the board itself — no-preview (an absence: the preview never comes), strict-count, countdown, three-hearts, unchecked — MUST show the line before the first move, or the player feels cheated. Differences that are visible in play (trios, moving cards, a larger board, a clock) still show the line; the board then confirms it.
- **Future families:** every new variant must supply its differing help text at design time — a differing step, note, or scoring row in `docs/puzzles/<id>.md` and in the manifest's `help` — that text _is_ its round-rule line. A variant with no differing help text at all fails review: either its rule did not actually change (fails C2) or its teaching is missing.
- **Template:** add this rule to `docs/puzzles/_TEMPLATE.md` in §7 alongside the visibility rule: "Every variant supplies one plain-language rule sentence for its round; the sentence is shown for that round only, never as a variant name."

## 6. Ranked integrity — reuse, do not rebuild

- `parseRun` / `saveRun` (`src/lib/server/runs.ts:28,120`): replay, timing, move cap, score-config version, ban/lifecycle, idempotency, and the unranked 100/hour cap stay exactly as they are. The daily path adds two checks and only two: the submitted seed + variant must equal the server's `daily_puzzle` for that family/date, and the player must not already have a ranked daily completion for that family/date (second completion is practice, unranked).
- Scoring: family `brief-v1` configs stay. A daily score is comparable _because_ every player that day played the identical puzzle — no normalisation, no difficulty weighting, no cross-variant maths. That is the universal pattern from the research (NYT, LinkedIn, Puzzmo, Dayzle) and the reason Puzzmo abandoned cross-game total points on 19 Oct 2026.
- Loss handling: a failed daily attempt saves no `daily_best` row, the ranked session is marked abandoned by exact session id, and the streak does not advance. A daily board entry is created only by a completed, replay-validated daily run.
