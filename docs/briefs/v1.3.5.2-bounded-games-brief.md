## Proposed complete .2 slice (subject to owner decisions and visual approval)

1. **Bound the overview, preserve its exact totals.** Keep the existing `/admin/games` family cards, aggregate cohort definitions, 60-second KV cache/fallback and invalidation on audited lifecycle writes. Do not return all per-variant cohorts/history for an unselected family merely to paint global totals. A summary cache shape/key change is permissible only with validation of old/malformed/stale values and safe D1 fallback; cache never authorizes starts or writes. Preserve family totals as the sums of exact per-variant cohorts, including disabled/never-played identities and legacy NULL-variant mapping. Do not replace the one-JSON-bind activity mapping with a bind-per-group query.
2. **Page the declared variants through the existing Games route.** Keep deterministic manifest/catalog order and bounded row data. Fetch only the visible slice's lifecycle, reconciled counts and labels, while still showing exact family/global counts independently of the page. Include disabled and never-played variants. Provide first/previous/next/last or equivalent reachable navigation with total/page status, stable URLs and safe empty/out-of-range behavior. A user must reach and manage every accepted variant without loading 100 rows; switching tab/family or returning from inspection must not strand them on an unrelated page. Do not alter action names, reasons, confirm fields, permission checks, audit or current-game availability enforcement.
3. **Group historical aggregates; fetch detail on selection.** Replace the per-variant `GROUP BY rules_group,score_config_version` fan-out with a family-scoped grouped query, then associate rows using the existing variant-to-leaderboard-group mapping. Preserve exact completed/ranked/hidden/best/average/duration and historical score-version identity; no unbounded list of historical versions may leak into the initial payload. Supply bounded paged family history and selected-variant history with explicit limits/next-page state, rather than the current `LIMIT 101` truncation for every variant. Inspect a selected variant on demand (and only that variant); retain a usable read-only detail/error/retry/close path, focus return, Escape/backdrop behavior, in-page state and scoring link. No all-variant history is required just to show summary rows. Unknown family/variant/page values must fail safely before querying or revealing data.
4. **Hydrate scoring only as needed.** On `/admin/games` Statistics/Settings, read only the live values actually needed for test play, without all score-version lists; on `/admin/games?game=…&subview=scoring` and existing `/admin/scoring`, preserve the existing complete editor/version/rollback experience and server-side scoring guards. Preserve a score shared by several variants as one immutable scope; a new history/selection path must not mutate score snapshots or issue a ranked session. If a selected detail needs a scoring reference, link to the existing editor instead of duplicating it.
5. **Measure and trim metadata only where justified.** Inventory actual browser and admin consumers before altering `scripts/generate-registry.ts` or generated projections. Retain fields required for player selection, help, presentation, scoring, test play and checkpoint/resume. Remove or split only measured unused/eagerly duplicated data; never hand-edit generated output or change catalog/manifest authority. If the existing projection is already minimal for these views, record that finding and **do not invent a new metadata system** to satisfy a size claim. Include any necessary generated output and directly affected small projection tests in the eventual owned-file list.

A preferred low-change direction for review is a same-route GET selection/page model and existing Games component, not a new public API or generic data layer. Exact parameter and detail-loading behavior remains a visual/UX decision below; no new route or migration is assumed. Keep the server's failure boundary: status errors rethrow; unexpected reads log `morphi:operator_read_failed` and render a safe unavailable state. If partial detail loading can fail independently, retain the current list and show a retryable, logged detail failure, never an empty success or a lost pending action. AccountForm errors/drafts and GameSwitch behavior must remain intact.

**Stop condition:** the existing Games overview, family Statistics, Settings, scoring, test play and every accepted variant work end to end through bounded list/detail reads at a synthetic 100-preset cap; there is no missing history or management action requiring .3 or later batches. No mechanics, Memory matrix, other-family expansion, schema migration by default, speculative index, generic cursor framework, 1,000-preset gate, new scoring policy, dependency upgrade or unrelated admin optimization. Do not claim an unmeasured speedup.
