## 2. Rules — from global research

Source: global Tangram research (11 Nov 2026, report + supplement). The rules below are this brief's own statements; no external file is required to build from them.

- **Core loop:** drag the seven tans from the tray onto the target silhouette, rotate (45° steps) and flip (parallelogram only) as needed, snap to the silhouette when close, until the silhouette is filled exactly. Solo silhouette-fill puzzle, not a picture puzzle.
- **The seven tans (unit square, area 1):** 2 large right triangles (area 1/4 each), 1 medium right triangle (1/8), 2 small right triangles (1/16 each), 1 square (1/8), 1 parallelogram (1/8). All triangles are right isosceles (45°, 45°, 90°). Total area always exactly one square.
- **Three classic rules:** (1) Use all seven pieces exactly once. (2) Pieces lie flat, may touch (edge or corner) but never overlap or stack. (3) Match the target boundary — no unintended gaps inside, no piece protruding outside. Every piece must touch at least one other (a single-point touch counts).
- **Rotation and flip:** rotation always allowed, 45° steps (tap / R; Shift+R the other way). Flip (F / Flip button) matters for one piece only: the parallelogram is the only chiral tan — its mirror image can be obtained only by flipping it over. Triangles and the square look the same turned over.
- **Win:** silhouette filled exactly with all seven pieces, no overlap, no gaps. **Lose (run over):** none in classic play. Lose states exist only in the countdown and mistake-limit variants (§3). Blocked is not a state — any arrangement can be rearranged freely.
- **Silhouettes (not variants, not boards):** the 13 convex shapes (Wang & Hsiung, 1942 — the only 13 convex configurations) + Cat, House, Bird, Boat, Swan. The silhouette is drawn from the seed stream inside `createRound` (Nonogram pattern, §4), NOT a `daily_puzzle` column — that table has no silhouette column. The only board is `(tangram, date)` — one identical daily puzzle per day.
- **Controls (demo-proved — see header):** drag to move; tap / R rotates 45°; F flips the parallelogram only (other pieces show "Only the parallelogram can be flipped"); H = Hint; arrows nudge the selected piece by one snap step; Hint, Reset (same seed, same silhouette) buttons. Pieces snap when a corner comes close to a silhouette corner or a placed piece's corner. Keyboard-only play was CONFIRMED in the v2 demo (House solved keyboard-only live).
- **Demo to copy:** artifact `tangram-middle-style-demo` (same engine as `tangram-two-column-demo`; 5 silhouettes proven exactly tileable: Pyramid, shed-roof House, Cat, Swan, Dog). **Use the demo as the visual and behaviour reference only — do not copy its code as production logic (demo has no seeded engine, no SplitMix64, no ranked timing, no server replay, no daily board).** If the demo cannot be opened, STOP and report.

## 4. Generation, determinism, fairness

- **RNG:** `createRng(seed)` (`src/lib/engine/rng.ts`, SplitMix64 v1 — verified at HEAD `0ccf018`: `createRng(seed: string)` with `nextU64()`). All draws from one stream in fixed order. Integer-only. **Banned in logic/manifest:** `Math.random`, `Date.now`, `performance.now`, `new Date`, float math (`Math.sqrt/pow/sin/...`). Enforced by ESLint + `scripts/check-boundaries.ts`.
- **Lattice (exact algebraic coordinates — no floats for geometry):** work in units of the small-triangle leg (u = 1). A unit edge (1,0) rotated 45° becomes (√2/2, √2/2) — irrational, so no fixed integer grid can hold every rotated vertex (§4A). Coordinates are exact algebraic numbers encoded with integers: each coordinate is an integer pair (p, q) representing p + q√2 in quarter-cell units. Q(√2) is closed under 45° rotations and translations, and every tan vertex in all 8 orientations lands exactly on this encoding with integer coefficients (verified: max denominator 1 across all 7 tans × 8 orientations). All engine arithmetic is exact integer arithmetic on the encoding; never compute √2 at runtime in logic. Precompute the 7 tan polygons in the algebraic encoding once (all 8 orientations); if any coordinate needs a float, the design is wrong — stop and report.
- **Pipeline (assemble-first, Lakolam precedent + PlayBoardGames guarantee):** seeded search lays tans down one by one, each sharing a stretch of side with one already down, turned any of eight ways (Lakolam: keep the shape only if its outline is one simple polygon with no holes, fitting the page, and perimeter²/area between 24 and 46); OR pick a frozen curated silhouette from the own-drawn library. Either way the assembly is stored as the witness. **Area alone never confirms solvability** (an 8×2 rectangle and a house shape both have area 16 and no arrangement — Lakolam). A silhouette with no witness is rejected; the generator never issues a silhouette it cannot solve.
- **Fairness gate (the hard rule):** a witness-verified silhouette only — never a random outline. Solving Tangram is NP-hard (irregular shape packing), so do not put a runtime exact solver in the normal path. A variant witness must be checked under that variant's rules (flip-off witness must not use the flipped parallelogram; double-14 witness in 14 pieces; falling-pieces witness is the same assembly — arrival order is presentation, not generation).
- **Uniqueness is NOT guaranteed — verification must accept any valid arrangement:** the square tile is interchangeable with the two small triangles when they abut along their hypotenuses; a trapezium has two layouts. Win detection is by exact polygon coverage, not by matching the stored arrangement: every piece polygon lies inside the target, no two pieces overlap, and the union area equals the target area exactly (8 units). A piece outside the target fails; an arrangement with a gap fails. The witness is stored for tests only — never used to judge a player's solution (Connect comment pattern).
- **Silhouette + attempts (Nonogram pattern):** silhouette drawn first from the seed stream; **100 attempts per silhouette, then reject the seed and advance the RNG stream**. Require the witness to be verified before issuance. Bound assemble-first attempts; do not add an exact solver to the request path.
- **Move shape:** numeric-only fields only, e.g. `{piece, x, y, rot, flip}` (piece 0–6, x/y exact algebraic coordinates encoded as integer pairs (§4A), rot 0–7, flip 0/1) / `{action}` (hint as a replayed action code, Nonogram `NONOGRAM_ACTION` pattern) — fix exact keys in `manifest.parseMove` with exact sorted-key validation like Connect (`'at,cell,pair,stroke'` — verified in Nonogram `manifest.ts` as `'at,cell,mark,stroke'`). Include `at` (monotonic ms) only if a timed variant needs it. Replay regenerates the round from the seed, re-applies moves via `applyTangramMove` (illegal move throws `RangeError`), and checks the exact polygon coverage is complete. Win is judged from player state.

## 4A. Geometry correction — exact algebraic coordinates (authorised narrowly, owner 2026-11-13)

Codex stopped before implementation under the brief's conflict rule: §4's lattice claim was false — a fixed integer quarter-cell grid cannot represent all rigid 45° rotations (a unit edge (1,0) becomes (√2/2, √2/2); √2 is irrational and no rational scaling makes it an integer). The stop was correct; no production files changed. This section authorises ONLY the correction below. No other §4 change.

1. Coordinates are exact algebraic numbers encoded with integers (§4 Lattice bullet, rewritten): each coordinate is an integer pair (p, q) representing p + q√2 in quarter-cell units (u = small-triangle leg = 1). Q(√2) is closed under 45° rotations and translations, and every tan vertex in all 8 orientations lands exactly on this encoding with integer coefficients (verified: max denominator 1 across all 7 tans × 8 orientations, and exact shoelace areas — 4 + 4 + 2 + 1 + 1 + 2 + 2 = 16 in the 4×4 square system).
2. All engine arithmetic is exact integer arithmetic on the encoding. The float ban in §4 stands: no floats in logic, manifest, generation or win-check.
3. The win check is exact polygon coverage (§4 Uniqueness bullet, §9 units, rewritten): every piece inside the target, pairwise non-overlap, union area exactly 8. It replaces quarter-cell coverage everywhere.
4. The move shape carries x/y in the integer-pair encoding (fixed exact keys in `manifest.parseMove`, same sorted-key validation).
5. The demo's tileability proof (exact-cover solver + shapely, union area exactly 8, zero overlap) still stands as the silhouette proof; the app re-proves it with the exact algebraic check, not with floats.
6. A unit test must prove every tan in all 8 orientations has exact integer-pair coordinates, and that the win check accepts any valid arrangement (uniqueness is NOT guaranteed — §4).

**UI-only projection exception (owner, 2026-11-13):** the View/Stage/motion may project exact coordinates to float screen coordinates for SVG rendering, pointer positioning and snap-distance display checks — the screen is inherently float, and pointer events arrive as floats. These floats are presentation-only: they never enter logic, manifest, generation, move validation or the win check. A pointer-derived position must be resolved back to an exact algebraic coordinate (snap to the nearest exact position) before any move is committed; the committed move carries only the exact integer-pair encoding. The engine's exact state is the single source of truth; the UI is a projection of it, not a second geometry. If any consumer outside the UI needs floats, stop and report — do not widen this carve-out silently.

## 5. Scoring, ranked integrity, ending

- **Scoring (`brief-v1`, DEFAULT — owner, 2026-11-13; admin-changeable any time):** `score = 1000 (completion) + piecesPlaced × 100 (double-14: ×50) + max(0, par − seconds) × 5 − 100 × hintsUsed`, floored at 0. Par (accepted as build values): classic/sei = 60 s, double-14 = 120 s, coloured-map = 30 s, no-full-size = 90 s, falling-pieces = 90 s. Coloured-map gets NO par/time bonus (the map removes the decomposition; a map time is not comparable to a silhouette-only time). `brief-v1` values are admin-editable; an edit changes future rounds only, never saved scores. No standard scoring exists in the wild (research §3; one published exception is Sugarizer's formula — see supplement §S1 — which mixes difficulty/level bonuses Morphi does not have, so it is cited, not copied). This formula is a Morphi design choice, carried from the Neopets shape (15 points per piece + time bonus).
- **Loss handling:** countdown timeout and mistake-limit exhaustion save NO daily-board row and no score; the failed board stays viewable; ranked session marked abandoned by exact session id (Batch A precedent from Nonogram). No sixth bucket: mirror Memory's move-cap loss recording.
- **Timing floor (5,000 ms — accepted as build value, owner, 2026-11-13):** manifest-owned minimum active time for a ranked claim. A daily Tangram is a seconds-long race (familiar solves 15–20 s), so a sub-5 s claim is a memorised / bot-shaped claim. A ranked claim below the floor is downgraded to unranked, not a ban. Implemented in `saveRun` per the v1.4.1 §8B rule already in code (`runs.ts:383`, verified at HEAD: `ranked = gameplayMs >= timing.minimumSeconds(result, run.variant) * 1000`; below-floor saves unranked with no daily-board row, consumes the attempt, no retry, no throw). Hidden tab: checkpoint on hide, ranked time is server wall-clock (Connect pattern).
- **Daily-attempt conflict (state it plainly):** Morphi's v1.4 single-attempt ranked play is a Morphi rule, NOT the wild Tangram norm. Wild daily Tangrams allow replays ranked by time (Omikuji: up to 30 submissions a day per level, server re-verifies every run; TangramFun: ranks by time and moves, a no-hint solve always beats a one-hint solve even if slower). This brief keeps Morphi's single-attempt rule and does not claim wild precedent for it. Hint-assisted solves are marked "solved with help" (PlayBoardGames pattern) and are not ranked equally with clean solves — the brief must state the marking rule, not leave it implicit.
- **Ending (manifest):** `kind: 'completion'` for clear; loss variants need a variant-level `ending` override with `run_over` kind. Headlines/subline keys per `_TEMPLATE.md` ending contract; `animation: 'fade-rise'`, `continue: 'auto_500ms'` (Connect/Nonogram pattern — verified in Nonogram `manifest.ts` — do not invent a third value). Presentation never decides end state or delays persistence.
- **Move cap:** `maxMoves` = 10,000 in the manifest (Nonogram pattern, verified). `maxSeconds` ≤7200 if present (countdown uses 120, not 1800); variant `weight` 1–10000; `messages[variant.name]` must exist.
- **Leaderboard groups:** the manifest must define **no** per-variant `leaderboardGroups`. The contract already permits omitting the field (§8A).
