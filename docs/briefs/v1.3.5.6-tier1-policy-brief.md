## 1. Scope, Purpose and Governing Constraints

### Core Purpose
Introduce **Tier 1 supported-dimension policy controls** for the Memory puzzle family in the operator admin workspace and server issuance pipeline.
Instead of relying solely on individual variant switches, Tier 1 lets operators narrow supported gameplay dimension values; archetypes are read-only summaries.

### Governing Constraints (C1–C10)
- **C1 (Scope/count):** Memory family only. Accepted catalogue remains the 10 pilot variants (4 baseline + 6 .5 additions). No new variants, preset IDs, or other-family expansions.
- **C2 (Variant identity):** No gameplay rule or scoring identity is modified. No new deals, seeds, or cosmetics.
- **C3 (Boundaries):** Self-contained, stoppable, commit-ready milestone. Delivers complete dimension policy modeling, server issuance enforcement, admin UI controls, audit logging, and cache invalidation without depending on .7 directory work.
- **C4 (Verification):** Focused, owned checks only (scoped formatting/lint, type check, Memory dimension units, real D1 policy issuance tests, Playwright admin browser tests). Full `bun run verify` remains deferred.
- **C5 (Visual gate):** Dedicated interactive preview fixture (`static/demo/v1.3.5.6-tier1.html`) must be reviewed and approved by the owner at **390×844, 844×390, and 1280×800** before actual admin UI integration.
- **C6 (Compatibility & Security):** In-flight sessions and already-issued rounds complete against their original immutable rules and scoring. Policy narrowing applies strictly to **authoritative new-round issuance** (`startRanked`, `variantAvailable`, `/api/play/availability`).
- **C7 (Smallest change):** Reuse existing D1/KV configuration patterns (immutable snapshots with parent rollback or audited lifecycle tables). No generic rule DSL, speculative table schemas, or external dependencies.
- **C8 (Authority):** No automatic progression, implementation, git commit, push, or deployment without explicit owner instructions.
- **C9 (Evidence):** Clearly distinguish candidates, implemented states, fixture layout tests, and owner visual/functional acceptance.
- **C10 (Portability):** Standard parent agent execution; no invented tools or model claims.

### Non-Goals
- **DO NOT** add any new gameplay variant or preset identity.
- **DO NOT** build an arbitrary, free-form rule builder (dimensions and supported values are finite and hard-coded in family code).
- **DO NOT** expand to other families (Block, Connect, Mahjong matrices stay UNPOPULATED).
- **DO NOT** alter or invalidate completed runs, existing leaderboard rows, or legacy replay hashes.
- **DO NOT** introduce audio, animations, or deployment operations.

## 2. Finite Dimension Matrix, Archetypes, and Pilot Variant Mapping

Family code owns the hard supported limits; admin policy can only **narrow** (disable) supported values.

### Supported Dimensions and Values (Memory Family)

| Dimension Key | Description | Supported Values (Family-Owned) | Default / Baseline |
| :--- | :--- | :--- | :--- |
| `matchSize` | Number of identical cards required to form a match | `2` (Pairs), `3` (Trios), `4` (Quads) | `2` |
| `opening` | Opening exposure before countdown/input starts | `preview` (3s preview then hide), `no-preview` (0s face-down) | `preview` |
| `movement` | Board dynamics and position behavior after a miss/match | `static` (cards stay in place), `moving` (full shuffle of unrevealed cards on miss), `swaps` (2 marked cards swap on miss), `collapse` (matched cards leave and survivors close gaps) | `static` |
| `backs` | Card back visual and informational structure | `uniform` (identical backs), `two-backs` (distinguishable dotted vs. striped backs per pair) | `uniform` |
| `budget` | Attempt allocation and run-over outcome | `standard` (6 attempts/group; unfinished stays on board), `strict` (2 attempts/group; run-over state without score) | `standard` |
| `availability` | Unmatched card interactive availability after a miss | `standard` (all unrevealed cards playable), `lockout` (last flipped card locked for next attempt) | `standard` |

### Memory Archetype Groups
To provide clear mental models for operators, variants are organized into six intuitive archetypes:
1. **Core / Standard Matching:** Standard 2-card match, preview, static board (`memory:classic`).
2. **Information & Visibility:** Alterations to opening preview or visible back patterns (`memory:no-preview`, `memory:two-backs`).
3. **Extended Grouping:** Larger card set requirements per match (`memory:trios`, `memory:quads`).
4. **Grid Dynamics:** Post-miss or post-match positional shifts (`memory:moving`, `memory:swaps`, `memory:collapse`).
5. **Resource Pressure:** Strict attempt limits with run-over outcomes (`memory:budget`).
6. **Turn Constraints:** Temporary card lockout penalties (`memory:lockout`).

## 3. Policy Precedence, Issuance Enforcement and In-Flight Safety

### Authoritative Precedence Rule
A variant is eligible for **new round issuance** (both solo selection and ranked session start) if and only if **all** of the following conditions hold:
```text
isAvailable = gameAvailable(family)
           && variantLifecycle(family, variant).state === 'enabled'
           && isDimensionValueEnabled('matchSize', variant.matchSize)
           && isDimensionValueEnabled('opening', variant.opening)
           && isDimensionValueEnabled('movement', variant.movement)
           && isDimensionValueEnabled('backs', variant.backs)
           && isDimensionValueEnabled('budget', variant.budget)
           && isDimensionValueEnabled('availability', variant.availability)
```

**Crucial Narrowing Invariant:**
- **Admin dimension policy overrides individual variant enablement:** If `matchSize: 4` is disabled by dimension policy, `memory:quads` **cannot** be issued, even if its row in `variant_lifecycle` is set to `enabled`.
- **Individual variant disable is preserved:** If all dimension values for `memory:no-preview` are enabled by policy, but `memory:no-preview` is individually disabled in `variant_lifecycle`, it remains disabled.
- **Specific override cannot bypass a disabled dimension:** An operator cannot bypass a disabled dimension without re-enabling that dimension value in policy.

### In-Flight Round Preservation
- Policy evaluation occurs strictly at **issuance time** (`startRanked`, `/api/play/start`, `variantAvailable`).
- When an operator updates dimension policy to disable a dimension, any player currently in an active round (ranked session within TTL or solo checkpoint) is permitted to complete their round under the original issued rules and scoring configuration.
- The server replay validator (`parseRun`, `saveRun`) checks only the cryptographic payload hash, seed determinism, and the issued session record—never blocking a valid completion because of a prospective policy change.

### Required Preview Elements & States
1. **Dimension Controls & Toggles:** Clean grouped toggle controls for each supported dimension and its values (e.g. `Match Size: 2 | 3 | 4`, `Grid Dynamics: Static | Moving | Swaps | Collapse`).
2. **Archetype Summaries:** Grouped view showing which archetypes are active, partially restricted, or disabled.
3. **Dynamic Affected-Preset Summary:** Instant visual feedback calculating how a policy change impacts the 10 pilot variants (e.g. disabling `matchSize: 4` flags `memory:quads` as "Disabled by policy: matchSize = 4").
4. **Invalid-Combination & Boundary Feedback:** Clear error messaging if an operator attempts an unsupported action (e.g. disabling all match sizes so zero variants would be playable while the family is enabled).
5. **Confirmation Dialog:** Dialog displaying the exact list of newly disabled/enabled presets, requiring operator reason (3–240 chars, no `@`/newlines) and an explicit confirmation checkbox before submission.
