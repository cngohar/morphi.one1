## Implemented local controls

`bun run admin:local -- --local prune-expired` requires enrolled OS identity, current TOTP and the database `admin` role. It atomically runs the limited cleanup above and writes an audit with cutoff values. Counts are printed without identities. This command has **no remote mode**, is not automatically scheduled, and was exercised only against isolated test D1 databases. It was not run against the owner's saved local data.

`bun run admin:local -- --local privacy-delete INTERNAL_USER_ID CASE_REFERENCE` requires the same authentication/role. Use only after the request procedure in `PRIVACY_REQUESTS.md` establishes the appropriate action and authority. It deletes the active user with FK cascades and writes an independent minimal audit. It is not an arbitrary SQL or impersonation interface. No other request evidence goes in the command line or audit reason.

Tests cover permissions, expired versus active state, continued ranked supersession, committed retries, unresolved-claim recovery, removed account/session/game rows, public leaderboard field allowlisting, and separate records intentionally surviving deletion. A production maintenance/operator path, cadence, monitoring, backup restore handling, and any audit expiry must be reviewed before enabling production accounts. Restores must reapply completed erasure decisions before serving restored data.

## Local v1 integration inventory — 2026-10-26

These describe local code, not an enabled production account/event service.
Web operator sessions store a hash of a random grant, Google session reference,
and timestamps. Grants expire after 30 minutes or 10 minutes idle; sensitive
actions require a Google session and second factor fresh within 15 minutes.
Expired rows become eligible for operator-invoked cleanup. TOTP secrets are
AES-GCM encrypted with a key derived from the existing auth secret; recovery
codes are hashed and single-use. Reset invalidates grants and replaces both
sets of material. Changing the auth secret requires the protected reset path.

Opt-in gameplay events contain a random event ID, hashed short-lived visitor
reference, coarse event/family/error enums and time. The browser cookie lasts
24 hours and is separate from account identifiers. New event ingestion deletes
up to 100 rows older than seven days; operator maintenance deletes all eligible
rows. Rows may remain longer if neither runs. Withdrawal stops collection in
that browser and requests deletion of events linked to its current cookie.
It cannot identify events from an already-expired cookie. DNT/GPC disable sending.

Rate-limit rows hold short-lived keyed hashes/counters and become eligible for
cleanup after their two-minute window. Moderation cases store opaque case IDs,
public target references, kind/state and time, never request emails/evidence.
Audits include self-service deletions so the local dashboard counts deletions;
they retain an internal target reference after active account records are removed.
Audits/cases have no automatic TTL; justified retention and production operations
remain owner release gates. The panel has no audit-delete or role-editor action.

## Local v1.1 theme inventory — 2026-10-27

Local `play_session` and `completed_run` rows now also retain theme configuration
and generator version IDs and a resolved cosmetic snapshot. They follow their
existing row retention and account-deletion cascades. Legacy rows retain the
`curated-v1` marker. This adds appearance data to existing rounds; it does not
introduce a new account identifier, expiry schedule or production service.

Browser IndexedDB `morphi-themes` retains the latest three dealt appearance
snapshots for freshness, including the seeds and cosmetic parameters. It holds
no name, email or account identifier and falls back to memory if storage is
blocked. It has no time-based expiry; new deals replace the oldest snapshot.
Clearing site data removes it. Pending replay entries also keep their resolved
appearance locally; the replay request sends version IDs, and the server uses
its issued snapshot or regenerates the solo appearance from the validated seed.

Local `morphi.block.played` and `morphi.memory.played` flags distinguish an
unplayed family from a completed zero-score round for the NEW tag. They contain
only `1` and remain until site storage is cleared or evicted. Theme history and
these flags are device data, not an account-owned cross-device history or an
operator-controlled remote wipe mechanism.

No theme seeds, snapshots or new theme fields were added to the optional
measurement endpoint. The published guest/privacy deployment is unchanged;
this inventory describes the authorized local build only.

Local Card integration (2026-10-28) adds `play_session.card_opening_ms`, a
server-owned numeric presentation allowance for authoritative timing. Earlier
rows default to zero. It follows the existing ranked-start retention/deletion
rules and introduces no additional identifiers or collection purpose.
